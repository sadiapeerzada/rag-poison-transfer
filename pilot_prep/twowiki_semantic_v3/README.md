## Checkpoints and resume

One writer holds a nonblocking filesystem lock. Raw record publication uses fsync plus same-directory atomic hard-link publication with no overwrite, and published files are mode 0444. This guards against accidental/API mutation, not a malicious owner changing both files and seals. Copy the final seal hash to independent custody after any future pilot.

Each request is durably reserved before a backend call; its prompt, token cap, derived seed and context are recorded. The raw `GenerationResult` is durably saved before semantic validation. A resumed V3 construction replays identical responses through the unchanged validator and reconstructs complete attempt logs, while only previously unstarted calls may reach the backend. Intent/response request bindings must match. A crash after intent but before durable response is unknowable: resume stops with `ResumeBlocked`, even if the backend might never have started. Do not delete or retry that intent. Recorded backend/infrastructure errors also block automatic continuation and remain separate from semantic failure. Infrastructure records preserve available attempt/raw-return information; unavailable output is explicitly absent.

Every reserved intent consumes the conservative global cap of 200, including ambiguous/error calls. Scientific retries remain bounded at two per document. All slots are attempted; incomplete intensity-3 constructions retain partials but have no injectible documents. Duplicates are retained/reported, not counted as independent corroboration. A complete 50-record seal binds result and call-journal byte hashes, context and call count. Resuming a sealed run verifies it without backend creation or rewriting results. No Dense/RCD/retrieval/QA stage exists.
